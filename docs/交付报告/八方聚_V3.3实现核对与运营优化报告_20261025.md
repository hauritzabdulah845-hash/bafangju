## 0. 一句话结论

**"规则引擎"基本做完了，"生意"还没做完。**

- **机制层（§4 核心规则）完成度约 85%**：阶梯定价、免单订单、分佣记账、排队分红、储备专户季度分红、提现拆笔/确认收款、审核降级开关，实体与测试都在，属于"文档写到的资金规则基本都能跑"。
- **可运营层完成度约 55%–60%**：**货不能发、款不能结、券不能卖、广告不能展示、数据不能看**。这五项不是体验问题，是"上线后第一周就会爆"的经营问题。
- **文档写了、代码没做**的关键商业闭环共 **6 条**：券核销计费（3%/5%）、方案 B 分佣、广告位展示与结算、交易履约（发货/收货/售后）、分佣自动结算、等级/有效人数/规模系数。
- **已实现但做错/有隐患的代码缺陷 15 处（§4 表）**，其中 3 处涉及资金或合规：分佣结算不跑批（P0-3）、团队长 8% 份额永久沉淀（D3）、`/api/payment/notify` 可伪造支付（D10）。
- **文档自身有 1 处硬伤**：§4.4 测算表里"分佣基数合计 12.32 元 > 周期可分配收益 7.20 元"，按 100% 分佣结构性超发 5.12 元；这是**文档层面的口径矛盾**，不是开发实现的错，但必须由甲方/财务拍板后修订。

### 1.1 先说明：这些地方做得扎实，建议保留（不要在下阶段重构掉）

1. **阶梯引擎是纯函数 + 快照**：`n = ⌈1/r⌉+1`、步长、第 k 单实付全部可推导，订单快照固化，改配置不追溯——这是最容易做错、这里做对的地方。
2. **免单订单用 `pay_type=FREE` + 自建流水**，正面绕开了"微信没有 0 元支付"的死路，且与微信支付流水分开对账。
3. **分佣全程记账、代码里没有任何分账调用**；收益账户"冻结→结算→余额"，退款按单回滚并对不足部分挂账、限制提现——同类项目里少见这么严谨。
4. **提现把商家转账的硬约束都实现了**：单笔 500/单日 2000 拆笔、待确认收款、72h 超时退回重发、挂账禁提现。
5. **资金全部整数分**，`splitEven/splitByWeights` 用最大余数法保证合计严格守恒，未发现浮点误差。
6. **幂等与审计**：支付回调、免单领取、任务、提现、核销、季度发放、团队长批次全部幂等键；审计 append-only 且落盘。
7. **合规护栏是"默认值"不是"口号"**：间推默认关、提现默认关、免单退款默认关、贡献分无兑付接口、降级开关可一键隐藏。
8. **测试密度**：91 个用例覆盖域逻辑（README 自述 63、旧报告称 74，均低于实际），说明开发是把资金规则当"核心资产"在写的。

## 5. 文档自身的 3 处口径问题（需甲方/财务拍板，开发无法自行修）

### 5.1 最严重：§4.4 的"分佣基数合计"大于"周期可分配收益"

文档 §4.4 表格自己给出了两个数：

- 周期合计 **可分配收益 7.20 元**
- 周期合计 **分佣基数 12.32 元**

而 §4.3 定义"分佣基数 = 可分配收益（按单计算，为负记 0）"，§4.5 的分佣比例合计 **100%**。于是：

```
分佣总支出 = 12.32 元  >  周期真实可分配收益 = 7.20 元
结构性超发 = 12.32 − 7.20 = 5.12 元 / 周期（10 元商品、r=20%、成本 3 元）
```

原因很简单：第 5 单（−1.62）、第 6 单（免单，−3.50）**被记成 0 而没有冲减前面的正数**。同理，文档说"分红池约 2.7 元"——在分佣已经超发 5.12 元的前提下，**这 2.7 元没有真实来源**。

> 这不是开发实现错误（`ladder.allocatableIncome` + `max(0,…)` 完全照文档执行），是**文档的财务口径自相矛盾**。三种修法（建议 ① 或 ②）：
> 1. **周期级汇总计提**：以"整个周期可分配收益"为基数，按周期结束后一次性计提（工程改动中等，但账实相符）；
> 2. **允许负单冲减**（当期不足挂账，从后续周期扣回）；
> 3. 提高 r（减少步数、减少负单），但这会牺牲"10/8/6/4/2/0"的传播卖点。
>
> 无论哪种，§4.3、§4.4、§18-5 的验收口径必须同步改写，否则财务 UAT 第一步就对不上账。

### 5.2 r 与集采成本的商业前提没落定，种子商品已经穿仓

- 文档 §4.4 结论：r=20% 要求"综合集采成本 ≤2.2 元/件才维持 20% 利润口径"，≤4.2 元"不打穿"。
- 当前种子商品 `p_rice`：标价 10 元、**成本 3 元**（`server.js:935`），税费/通道费/运营成本三项均为 0（见 P0-10）。
- 用种子数据跑一圈：6 单实付 30 元、6 件成本 18 元、毛利 12 元；而按 §4.3 口径的分佣基数合计 **16 元**（700+500+300+100+0+0，两张负单被记 0）。其中直推 70% + 团队长 8% 的当期实际支出即 **12.48 元，已经超过 12 元毛利**；再加待支付的池内 3.52 元，每周期净现金流约 **−4 元**（还未计物流、客服、税务、支付通道费）。

→ 这是"待确认事项 12/13"的量化后果：**甲方不定 r 与集采价，上线即亏**。建议把"10 元区 r + 集采成本红线 + 物流费归属"打包成一次商务决策。

### 5.3 分红机制"发得出、用不掉、看不见"

- 排队分红与季度分红都进 `dividendBalanceFen`（"消费余额、不可提现"），但**没有任何下单抵扣入口**（检索 `dividendBalanceFen` 仅见累加与展示）。用户账上有一串数字，永远花不出去。
- 季度分红 V1 门槛"团队季度真实消费 5 万"——按当前种子价（10 元/单），一个 V1 团队需要 **5000 单/季**才能达标。对普通用户=永远不达标，对头部=门槛过低。
- 排队分红早期每席金额极低：按种子数据每个周期入池 3.52 元，首日 5% = 0.176 元；即使跑到稳态，每席也仅与"单周期入池额"同量级（个位数元）。

→ 建议：① 消费余额支持下单抵扣（并明确"抵扣属营销费用，不进分佣基数"）；② 三门槛给出"进度条 + 预计达标"的用户可解释界面；③ 排队分红设置"最低席金额展示位"或改为"批次开奖"叙事，做预期管理。

## 6. 运营总监视角：值不值得优化、先做哪一个

### 6.1 我的基本判断

这套产品的**规则内核是可信的**（阶梯即优惠、不承诺返现、只分真实利润、贡献分不兑付），合规护栏写得比多数同类项目扎实。但它现在更像"一个能演示的模式"，还不像"一门能经营的生意"。原因不是功能少，而是**三条链路断着**：

1. **钱的链路断**：分佣不解冻 → 推广者拿不到钱 → 没有推广者。
2. **货的链路断**：不能发货/收货/售后 → 用户不敢复购 → 复购率指标（≥25%）无从谈起。
3. **收入的链路断**：券不计费、广告不展示 → 平台只有成本没有收入。

**所以我的排序建议是：先修"钱"和"货"，再谈"券和广告"，最后做"数据和增长"。** 反过来的顺序（先做首页装修、先做看板）会让团队在错误的数字上做优化。

   现在能给的只有"券 + 广告位 + 到店客流"。但券没有 C 端入口、广告位不展示 → **首期商家会认为被收了钱没效果**。建议首期改为"免费入驻 + 券免费 + 广告位按效果后付"，把"商家案例"先做出来，比收 3000 元/月重要得多。
2. **10 元区到底定哪个 r？**
   这是全盘定价的锚。r=20% → 6 步（好传播、要求成本 ≤2.2 元）；r=39%–59% → 3–4 步（成本压力小、但"10/8/6/4/2/0"的故事没有了）。**建议先用 3–4 步小范围跑通财务模型，再决定是否上 6 步**——用 6 步做传播、用 3 步做账，是两套成本结构，不能混。
3. **推广者的钱从哪来、什么时候能提？**
   商家转账要"入驻满 90 天"。也就是说**上线前 3 个月推广者只能看到"冻结中"**。这必须写进推广话术与规则页，并给一个替代方案（例如前 3 个月以"消费余额 + 兑换券"结算），否则第一批推广者会在第 2 周集体质疑"是不是不给了"。

| 生产护栏 | 配置 `WX_APPID + WX_SECRET` 后禁止无 code 的昵称登录（400），杜绝绕过微信身份 |

**验证**：`npm test`（新增 `auth.test.js` 两例：devSeed 幂等、老账号认领；`authz.test.js` 新增"同一 deviceId 多次登录返回同一 userId"）；手工：清空小程序缓存后连续登录两次，`userId` 应保持不变。

### 9.10 V3.10 支付前端（本次）

**改前**：前端从不调用 `wx.requestPayment`，下单后直接打 `/api/payment/notify` 把订单改成已支付；后端 `prepay` 只返回 `prepay_id`，**没有生成小程序支付签名**，即使配了商户号也调不起微信支付。

| 项 | 实现 |
| --- | --- |
| 支付签名 | `buildJsapiPayParams`：`appId\ntimeStamp\nnonceStr\nprepay_id=xxx\n` 商户私钥 RSA-SHA256 签名 → `timeStamp/nonceStr/package/signType/paySign` |
| 预下单 | 登录态 + 只能给自己的待支付订单；openid 取自会话；同通道幂等、切模式或超 90 分钟自动重下 |
| 模式开关 | `PAY_MODE=mock/live`，未设置按配置自动判定；live 缺配置直接报错（不静默降级） |
| 模拟支付 | 仅 mock 模式可用，且只能操作自己的订单 |
| 客户端 | `api.payOrder()` 真实模式唤起微信支付、mock 直接入账；`waitPaid()` 轮询订单状态 |
| 订单查询 | 新增 `GET /api/orders/:id`（仅本人） |
| 环境探测 | `GET /api/payment/config` 返回当前模式（无密钥） |

**验证**：`npm test`（`pay.test.js` 新增 3 例：模式判定/live 缺配置报错、签名可用公钥验签、下单返回 payParams 且缺 openid 拒绝；`authz.test.js` 新增"只能为自己的订单预下单/模拟支付"）。**配置即生效**：不配参数走 mock；配齐 `WX_MCHID/WX_APPID/WX_MERCHANT_SERIAL/WX_PRIVATE_KEY`（+ `WX_PLATFORM_CERT/WX_APIV3_KEY` 验签）自动切 live；`PAY_MODE` 可强制指定。

**顺带修掉**：① `express.json()` 先于回调路由解析，导致 `notify-wx` 拿不到原始字节、**真实验签必失败**（改为 `verify` 捕获 `req.rawBody`）；② `express.json()` 默认 100kb，而上传 4MB 图片的 base64 ≈5.4MB，**商家上传广告图必然 413**（上限提到 8MB）。

## 结语（一句话给决策者）

**这份代码的"合规模板"比它的"经营能力"成熟得多**：规则写得克制、幂等与审计做得认真、资金全部整数分记账，这些都值得保留。经过 V3.4–V3.10 七个批次，**原 P0 清单已全部落地**：分佣结算、履约闭环、券与广告变现、鉴权收口、商家账号密码、用户登录 code2session、支付前端（真实参数就绪即生效）。剩余为 P1/P2：等级体系与有效人数、消息 6 类与订阅消息、支付结果页、后台缺失页签、埋点看板、LBS 等。**建议下一步把预算放在"真实月度对账 + 单商圈灰度"**，用 5 个经营指标验证，再决定是否扩量。
